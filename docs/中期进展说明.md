## 3. 本阶段完成的工作

### 3.1 统一处理流水线（解决 1.2 版遗留缺陷）

1.2 版的 `main_test.py` 按 `detect_rectangles(path, min_area=...)` 调用，而
`src/detectors/shape.py` 的签名是 `detect_rectangles(img, img_shape, min_area=...)`，
两者不一致，形状检测一路直接抛异常；同时 `main.py` 是空文件，脚本里还有 `cv2.waitKey(0)`
阻塞调用，无法在无界面环境运行。

1.3 版把所有能力收敛到一个 `VisionPipeline`：

```
图像 → 颜色路预处理 → 颜色分割 ─┐
     → 形状路预处理 → 形状判定 ─┴→ 中心距 + 短边一致性融合 → 目标列表 → JSON / 串口
```

* 配置集中在 `src/core/config.py`（数据类 + 4 个预设 + JSON 存取）；
* 结果统一为 `Target` / `FrameResult`（`src/core/result.py`），可直接序列化；
* 入口统一为 `main.py`（单图 / 批量 / 摄像头，支持 `--json`、`--serial`、`--quiet`）；
* `main_test.py` 改为无窗口冒烟脚本，作为最小调用示例。

### 3.2 颜色检测增强

* 保留原 HSV 阈值 + 形态学开闭链路；
* 新增**通道主导度约束**：要求主通道明显强于其余通道（红：R > 1.5·max(G,B)）。
  依据是实测 `data/test001.png` 中各色块的平均 BGR —— 纯红块 R/max(G,B) ≈ 2.6–3.6，
  而粉、品红、紫块仅 ≈ 1.3，据此可把这些"色相落进红色区间但颜色不纯"的干扰物剔除；
* 主导度按**轮廓平均色**判定而非逐像素判定：实测逐像素版本每帧多花 10 ms 以上且易被高光带偏，
  按轮廓判定只多花约 1 ms。

### 3.3 形状检测与颜色-形状融合

* 矩形：三通道 Canny 合并 → 膨胀闭合 → 轮廓近似为 4 点 → 内角 70°–110°、
  凸度 ≥ 0.8、宽高比 ≤ 10 三重判据；
* 圆形：圆形度 = 4πA/P² ≥ 0.75、最小外接矩形长短边差 ≤ 20%、排除四点近似的方形；
* 融合：颜色块与形状按中心距离（≤ min(30 px, 0.5×短边)）与短边尺寸一致性（≥ 0.45）配对，
  配对成功才判定为 `(颜色, 形状)` 目标，否则保留为 `颜色/unknown`。

融合的直接收益：同色异形干扰（红色矩形）不再被当成靶标，
端到端精确率由 **0.500 → 1.000**（见 §4.1）。

### 3.4 预处理：从"一条链路"改为"双路"

原 `Launcher_aim.preprocess_frame` 存在两个问题：

1. **锐化核归一化错误**：`kernel/9` 的核和只有 1/9，整幅画面被压暗到 1/9；
   已修正为核和为 1（1.3 版 `enhance.py` 与新 `Launcher_aim.py` 均已修正）；
2. **颜色路与形状路共用同一套增强**：实测 CLAHE + 锐化会把 Canny 边缘打碎，
   圆形召回从 0.988 掉到 0.350。

因此改为双路：颜色路做 V 通道 γ 校正（保色相），形状路只做轻降噪、不锐化。

### 3.5 串口通信协议实现

按 `Material/串口通信协议.docx` 实现 `src/comm/protocol.py`：

```
AA BB | LEN | ID(1) X(2) Y(2) CONF(1) CLS(1) | CRC16(2) | CC DD
```

* CRC-16/MODBUS，校验范围 = `LEN + 有效数据`；
* 支持 v2 扩展（追加距离 2 字节 + 状态标志 1 字节，`LEN=10`，与文档中"读长度=10"一致）；
* 流式解析器处理**分片、粘包、噪声前缀、长度非法、CRC 错误**，任何错误只丢 1 字节并重新同步到下一个帧头；
* 目标类别编码：十位为颜色、个位为形状（红圆 = 0x11 = 17），与文档"目标类别 1 字节"对应；
* `SerialLink` / `LoopbackLink` / `NullLink` 三种链路，便于真实设备、无硬件联调与纯离线调用。

### 3.6 量化评测体系（本阶段新增）

| 工具 | 作用 |
|---|---|
| `tools/make_dataset.py` | 生成 200 张 640×480 带真值的合成图，5 类场景 × 40 张 |
| `tools/benchmark.py` | 3 种配置 × 5 类场景，输出召回/精确率/形状准确率/中心误差/耗时，并出图 |
| `tools/exp_preprocess_ab.py` | 预处理链路对比实验（5 种方案） |
| `tools/exp_protocol.py` | 协议抗干扰实验（比特翻转、噪声前缀重同步） |
| `tests/` | 29 个单元测试用例（协议编解码、断帧重同步、流水线、预处理） |

评测口径：
* 匹配容差 = max(15 px, 0.35 × 目标尺寸)；
* **端到端召回/精确率** = 把系统输出直接当作靶标坐标时的召回/精确率（颜色单路输出全部红块，融合输出红圆）。

## 4. 关键实验与结论

### 4.1 融合 vs 颜色单路（200 张合成图）

| 场景 | 配置 | 端到端召回 | 端到端精确率 | 中心误差均值 | 平均耗时 |
|---|---|---|---|---|---|
| 正常光照 | 颜色单路 | 1.000 | 1.000 | 0.01 px | 3.8 ms |
| 正常光照 | 颜色+形状融合 | 0.988 | 1.000 | 0.01 px | 22.8 ms |
| 复杂背景（含同色矩形） | 颜色单路 | 1.000 | **0.500** | 0.35 px | 4.6 ms |
| 复杂背景（含同色矩形） | 颜色+形状融合 | 0.988 | **1.000** | 0.24 px | 25.2 ms |
| 过曝 + 模糊 | 融合 | 0.975 | 1.000 | 0.04 px | 19.5 ms |
| 目标遮挡 | 融合 | 0.950 | 1.000 | 1.05 px | 18.6 ms |

结论：融合以约 18~20 ms 的额外开销，换取了复杂背景下精确率翻倍（0.500 → 1.000），
在"目标类别判定"这一核心任务上是必要环节。

### 4.2 低照度：预处理是"能不能检出"的开关

| 方案（低照度 40 张） | 颜色召回 | 形状召回 |
|---|---|---|
| 不处理 | 0.325 | 0.988 |
| CLAHE + 锐化 | 0.338 | 0.225 |
| V 通道 γ + CLAHE + 锐化 | 0.975 | 0.350 |
| **V 通道 γ + 弱 CLAHE + 不锐化（采用）** | **1.000** | **0.988** |

机理：暗场目标像素 V≈88，低于颜色检测阈值 V≥100，无论形态学怎么调都检不出来；
V 通道 γ 校正把 V 抬到 130 以上即可检出。注意不能对 RGB 三通道分别做 γ——实测会把
暗红色的色相从 H≈178 推到 H≈12，直接掉出红色阈值区间；只在 V 通道缩放才能保持色相。

### 4.3 协议抗干扰（每组 3000 帧）

| 破坏方式 | 漏检帧（错帧被当有效帧） | 拒收率 |
|---|---|---|
| 1 / 2 / 3 / 5 / 8 bit 随机翻转 | 0 | 100% |
| 帧前混入 4 / 16 / 64 字节随机噪声 | 0（全部正确重同步） | 100% |

## 6. 目前存在的问题

1. **粘连目标**：相邻同色目标在形态学闭运算后连成一块（`test002.png` 有 2 处），
   颜色块中心偏移导致形状配对失败。
2. **相近色相**：粉/品红/紫色块在弱光或阴影下会进入红色阈值；主导度约束可缓解，
   但 `test001.png` 这类高饱和彩色场景仍有误检。
3. **形状检测耗时占比过高**（复杂真实图 50 ms/帧中占 46 ms）：三通道 Canny + 8×8 膨胀 +
   全图轮廓，未做 ROI 与降采样优化。
4. **C++ 移植不完整**：仅 `opencv.c/color_detector.*` 完成；`main.cpp` 里 `preprocessor.h`、
   `mask_utils.h`、`file_utils.h` 尚未实现，本机也没有 OpenCV C++ SDK（`C:\opencv` 为空），
   需在树莓派上配置工具链后一并完成。
5. **嵌入式未上板**：开发板、摄像头、下位机均未到位，实时性指标只在 PC 上验证。
6. **无相机标定**：只输出像素坐标，未做畸变校正与像素→世界坐标映射。
7. **真实样本太少**：仅 4 张真实测试图，泛化性结论以合成数据为主。
